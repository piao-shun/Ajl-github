# 踩坑记录

按「现象 → 排查 → 根因 → 修复 → 教训」记录。每条的修复都有对应 commit，可追溯。

## 1. requirements.txt 两个包粘在一行，云端部署直接失败

**现象**：Streamlit Cloud 构建失败，卡在依赖安装阶段。

**排查**：本地执行 `pip install -r requirements.txt --dry-run`，pip 报无法识别的包名；逐行检查文件，发现某一行是 `python-multipart>=0.0.9pytest>=8.0`——两个包粘在了一起。

**根因**：往 requirements.txt 追加 `pytest` 时漏了换行，pip 把 `python-multipart>=0.0.9pytest>=8.0` 当成一个不存在的包名。本地没暴露是因为本地早就装好了这些包，只有在干净环境（云端）才会炸。

**修复**：拆成两行（commit `86054c8`），修复后用 `--dry-run` 确认全部依赖可解析。

**教训**：改完依赖文件必须先跑 `pip install -r requirements.txt --dry-run` 再提交。「本地能装」不代表「requirements 写对了」。

## 2. 方向诊断表格五行全部显示「未体现」（把 item 文本当主键匹配）

**现象**：线上用真实简历做方向诊断，表格五行全部标「（模型未返回此项）」，调试面板命中序号是空列表——但模型明明返回了 5 行完整数据。

**排查**：展开调试面板看模型原始返回：5 行都在，只是 `item` 文本与行业标准有细微差异（少一个空格、换了一个说法）。

**根因**：`normalize_direction_result` 当初用 `item` 文本做 dict 主键严格匹配。模型返回的 item 只要多一个空格、换一个词、或换了 key 名，就全部匹配失败，一行都对不上。

**修复**（commit `b35988a`）：prompt 要求模型额外返回 `index`（1..N，对应标准条目序号），normalize 优先按 index 对齐，item 文本归一化后匹配做兜底，表格展示一律用 profile 自己的文字。随后又发现归一化会把 `C++`、`C#` 和 `C` 视为同一条，改为只保留 `+` 和 `#`（commit `6095a6b`）；并把校验从「数行数」改成「数唯一项」，重复 index 不再被误判为完整（commit `3776e78`）。

**教训**：模型返回的字段不能当外键用——它永远是「近似文本」。两个系统之间的对齐要靠协议字段（序号），展示要靠标准源；写归一化规则前先想清楚哪些字符有业务含义（`+`、`#`）。

## 3. 模型确实没返回 table（输出结构不稳定），和第 2 条是两回事

**现象**：另一次调用，返回的 JSON 里有 summary 但 `table` 字段整个缺失；旧版调试面板只截取 table 字段，显示为空，等于没提供任何信息；页面照样渲染成五行「未体现」。

**排查**：先怀疑是第 2 条的匹配 bug，但匹配逻辑刚修过；对比多次调用结果，确认同一 prompt 的输出结构本身不稳定——有时有 table，有时没有。

**根因**：代码对「缺 table」完全没有校验，空结果被静默渲染成「全部未体现」，把系统故障伪装成了用户的简历缺失。

**修复**（commit `4a380f4`）：新增 `_validate_direction_data` 结构校验；不合格时带着具体问题单次重试；两次仍不合格就明确报错，error 态绝不携带 table；`_debug` 改存整段模型返回前 800 字。后续（commit `4610e38`）发现行数不足也会静默通过，补了行数校验和「部分成功」态：两次都不完整但表格非空时，照常渲染表格并顶部警告，缺失项统一标「（本次未返回）」，与「简历真没提」区分。

**教训**：模型输出必须校验——静默失败比崩溃更危险；「模型出错」和「简历没写」必须在界面上彻底分开；调试信息要能回答「模型到底返回了什么」，否则等于没提供信息。

## 4. Secrets 里的 Key 曾以截图形式外泄，必须轮换

**现象**：一张对外展示的截图里，DeepSeek 的 API Key 以明文出现。

**排查**：人工检查发现截图包含完整 Key 明文。

**根因**：截图前没有遮盖敏感信息。Key 一旦离开 `.env` / Secrets 的受控范围（截图、聊天记录、issue），就进入了不可控的传播面，删截图也收不回来。

**修复**：立即在 DeepSeek 控制台轮换 Key 作废旧 Key，更新 Streamlit Cloud 的 Secrets，并确认旧 Key 已失效。

**教训**：截图、录屏、演示前先遮 Key；Key 泄露的标准动作是轮换而不是删截图；Key 只应该存在于环境变量里，绝不写进代码、文档、issue。
